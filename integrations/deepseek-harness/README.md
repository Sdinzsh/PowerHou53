# Powerhouse + DeepSeek Harness

## What runs where

OpenCode remains the main agent. Its Powerhouse plugin owns durable task records,
verification checks and checkpoint recovery. `powerhouse_harness` drives the
official `@deepseek-ai/dsh-sdk-client` over its owned stdio subprocess. The full
`sdk` profile supplies Harness's own tools, sessions, compaction and goal plugins.
The two runtimes do not share an agent loop or a permission system.

This implementation adapts Harness's durable-goal and event-journal ideas to
OpenCode; the native task store is first-party code, not imported Cordis plugins.
Automatic continuation is not enabled in OpenCode. Checkpoints persist work;
they do not launch unattended model turns.

## Setup

Requirements: Node.js `^22.19.0 || >=24.0.0`, Python 3.10+, Git and bash for this
repository's checks. Run from the repository root:

```bash
npm ci --prefix .opencode
npm ci --prefix integrations/deepseek-harness
bash tests/run_all.sh
node --test tests/integration_opencode.mjs
```

The last command additionally needs OpenCode on PATH. Tested versions are recorded
in `.opencode/PROJECT.md`. Dependencies are pinned in both manifests and lockfiles;
Harness is a developer preview, so upgrade with the integration tests.

Restart OpenCode from this directory. Local plugin discovery loads the tools
automatically; no global configuration replacement is needed.

Native task tools need no API credential. To delegate real model work, provide
`DEEPSEEK_API_KEY` through your usual environment or secret manager before starting
OpenCode. Do not put it in `powerhouse.json` or source control. The bridge defaults
to `deepseek-official` / `deepseek-v4-flash` using Harness's `sdk` profile. Set the
model, provider, timeout and per-request output cap in `.opencode/powerhouse.json`.
`maxTokens` limits each model response; the wall-clock timeout bounds the whole run.
It is not a total token or cost budget.

## Token-efficient defaults and learning

| Model-facing content | Default limit |
| --- | --- |
| Routine task recovery | 1,200 characters (`contextChars`) |
| Compaction recovery | 4,000 characters (`compactionChars`) |
| Successful check preview | 800 characters (`successOutputChars`) |
| Failed check preview | 4,000 characters (`failureOutputChars`) |
| Harness response preview | 6,000 characters (`harness.responseChars`) |

Task mutations return the revision, status and check results. `status` returns a
concise view; use `{"action":"status","detail":true}` for all saved task text.
Full objectives, criteria, checkpoints and evidence remain in the journal. Routine
prompts omit internal hashes/timestamps/revision counters and completed tasks.
Compaction retains a larger recovery summary; use status for anything abbreviated.

Long check output is available through the returned `outputPath` (up to the
runner's retained 12,000-character tail). Read that file when diagnosing failures.
Long Harness responses return `responsePath` with the full response; their preview
keeps the beginning and ending. These runtime logs stay local under the ignored
`.opencode/powerhouse/` directory. Preview limits do not reduce the tokens already
generated by a child; they reduce what gets sent back into the parent context.

Learning remains deliberate: retrieve relevant prior lessons, verify the work,
then record a non-obvious lesson/correction once or improve an existing skill.
Routine successes and duplicate notes do not need reflection. No extra background
LLM reviewer is launched. This improves reusable project memory and procedures;
it does not retrain model weights. Startup uses bounded memory snapshots, targeted
knowledge sections and recent history, rather than entire growing logs.

Use direct work for small tasks and one delegation route for each useful subtask.
The full Harness profile, verification gate and 8,192 per-request model output cap
are preserved. Actual token use depends on the selected models and task; these
limits are characters, not a promise of a particular bill reduction.

## Use from OpenCode

For a substantial task, tell OpenCode:

> Track this implementation with powerhouse_task. Save the acceptance criteria,
> checkpoint progress, run the suite with powerhouse_verify, and complete the task
> only after current checks pass. Use powerhouse_harness for a bounded specialist
> task when useful, then inspect its changes and verify locally.

The tool sequence is:

1. `powerhouse_task {"action":"status"}` — get current state and revision.
2. Start with that revision, an `objective`, `criteria`, and optional check names:
   `{"action":"start","revision":0,"objective":"Fix the issue","criteria":["Regression check passes"],"checks":["suite"]}`.
3. Use `checkpoint`, `block`, or `resume` with the latest revision and a `note`
   where required. Reuse returned revisions; read status when unknown, after
   editing-tool activity, or on a stale-revision error.
4. `powerhouse_verify {"check":"suite"}` — executes the configured argv without
   shell interpolation, captures bounded output, and records the real exit code.
5. Complete with the current revision and a note explaining acceptance. Each
   selected check must have succeeded against the current workspace.

Delegation uses `powerhouse_harness {"prompt":"<bounded task and acceptance criteria>"}`.
The result includes the child session ID and journal location. A completed child
turn is not proof that the requested implementation is correct. Empty responses,
failed or token-limited turns, cancellation and timeout are reported as errors.
The owned subprocess is closed on every exit path. Each call starts a fresh child
session; previous child journals remain available under the parent session's home.

## Verification and permissions

Configure named checks as `{ "command": "bash", "args": ["tests/run_all.sh"],
"timeoutMs": 120000 }`. The model chooses a name, not arbitrary command text.
The verifier enters OpenCode's `bash` permission gate; delegation enters the
`powerhouse_harness` permission gate. Existing OpenCode policy decides allow/ask/deny.

Once delegated, Harness owns child tool permissions. OpenCode does not review each
child tool call. The default full profile uses its own workspace/sandbox policy;
SDK approval forwarding is not implemented upstream. A request requiring child
approval can fail or wait until the bridge timeout. Use a configured Harness policy
appropriate to the project. `sdk-minimal` is available only by explicit config and
uses upstream's `danger-full-access` policy; it also omits compaction and other full
profile features. The bridge does not silently switch to that profile.

The verifier hashes Git-tracked and nonignored untracked file contents, modes,
symlink targets and deletions before/after a check and at completion. Known editing
tools clear evidence proactively. A failed rerun clears the older passing result.
Ignored dependency/build directories are outside this fingerprint; when changing
those inputs, rerun checks. Checks cannot prove semantic acceptance criteria;
the final completion note remains the agent's assessment. There is no global block
on ordinary assistant text: the evidence gate governs `powerhouse_task complete`.

The native verifier requires Git, rejects submodules/non-file entries, and bounds
each file at 32 MiB. Use checks that do not edit source files. Ignore generated
artifacts appropriately. Journals are excluded from fingerprints to avoid
invalidating a check when it records its result.

## Storage, recovery and rollback

Runtime state lives in ignored `.opencode/powerhouse/`: hashed parent session IDs
separate native `sessions/` journals and Harness `harness/` homes. Task mutations
use revision checks, an exclusive writer lock, atomic replacement and checksummed
JSONL records. These checks detect corruption; they are not a security boundary
against a process that can edit project files. State directories reject symlinks.

System-context and compaction hooks restore a bounded objective/checkpoint summary.
Resume the same OpenCode session to recover its task; a new session starts empty.
An interrupted journal write can leave `events.jsonl.lock`. After confirming no
writer is running, back up the session directory and remove only the stale lock.
Restore corrupted journals from a known-good backup. The journal limit is 8 MiB;
move to a new OpenCode session when reached.

To disable delegation, set `harness.enabled` to `false`. To disable all new tools,
move `.opencode/plugins/powerhouse.js` out of the plugins directory and restart
OpenCode. Preserve `.opencode/powerhouse/` for later recovery. Loop Guardian is
independent. For another project, copy the plugin, `powerhouse-*.mjs` helpers and
`integrations/deepseek-harness/` without `node_modules`; merge the plugin dependency,
configure checks, and add `.opencode/powerhouse/` to its ignore rules.

## Research and validation

The implementation follows these official references (reviewed 2026-09-15):

- [Harness SDK client](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/sdk/client): owned runtime, receipt-to-idle results and close-on-cancel lifecycle.
- [Harness goal group](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/goal): persistent objectives are separate from automatic continuation.
- [Harness compaction](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/compaction): full runtime context management.
- [OpenCode plugins](https://opencode.ai/docs/plugins/) and [custom tools](https://opencode.ai/docs/custom-tools/): factories, permission context and compaction hooks.

`tests/test_powerhouse.mjs` exercises state, permissions, evidence and lifecycle
failures. `tests/test_harness_runtime.mjs` boots the real full Harness runtime
against a loopback HTTP model fixture with a dummy key and isolated home; no paid
provider is contacted. `tests/integration_opencode.mjs` boots an isolated OpenCode
server and checks actual tool discovery. These validate the integration mechanics,
not the quality of a live model's coding decisions.
